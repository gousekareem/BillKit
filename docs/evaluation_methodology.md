# Evaluation methodology

## Sets

| Set | Location | Status |
|---|---|---|
| **HR assignment set**: 15 real bills + 5 non-bills, supplied by the candidate | `dataset/hr_assignment/` | **Pending.** The images were not available in this environment. `npm run eval:hr` writes a PENDING report until they are added |
| Synthetic smoke set: 10 fictional receipts + 5 non-bills, generated by `ai/scripts/synthetic.ts` | `evaluation/synthetic_smoke/` | Run. It is only a pipeline/harness check, **not** an accuracy estimate |
| Real development/test sets (licensed or consented) | `dataset/processed/{train,validation,test}` | Empty; see `docs/dataset/acquisition_guide.md` |

The HR images are evaluation data only. They are never used to tune rules, thresholds, calibration or models (see "Leakage" below).

## How to run the HR evaluation

1. Put the 15 bill photos in `dataset/hr_assignment/15_real_bill_images/` and the 5 non-bills in `05_non_bill_images/`. Name them so they match `file_name` in `ground_truth.csv`.
2. Fill in `ground_truth.csv` **from the paper bill**, not from the app output. Required columns: `expected_class`, `expected_merchant`, `expected_date` (ISO), `expected_total`, `expected_currency`, `expected_category`. Recommended: `difficulty`, `conditions` (e.g. `crumpled;low_light`), `source`.
3. Run `npm run eval:hr`, optionally with `-- --allow-vlm` to allow the cloud model when it is configured, and `-- --date-order MDY` for US receipts.
4. Outputs go to `evaluation/results/hr_assignment/`: `predictions.csv` (one row per image: expected vs predicted, correctness, uncertainty status, quality score, failure reason, processing ms, VLM use and cost), `results.json`, `metrics.json` and `report.md`.

## Matching rules

| Field | Counted correct when |
|---|---|
| Classification | predicted label = expected (`ambiguous` counts as wrong) |
| Merchant | after normalisation (lower-case, accents and punctuation removed, `&`→and, legal suffixes such as Pvt Ltd/LLP removed): equal, or one contains the other (both ≥ 4 chars), or Levenshtein similarity ≥ 0.85 |
| Date | ISO dates are equal |
| Total | equal within 0.01 |
| Category | case-insensitive equal |
| All required | merchant, date and total all correct |

Fields are only evaluated on images that are expected to be bills and that have ground truth for that field.

## Metrics

- Classification: accuracy, precision, recall and F1 for the *bill* class, a confusion matrix, and the number of ambiguous decisions.
- Per-field accuracy with **Wilson 95 % confidence intervals**. With n = 15 one error moves accuracy by 6.7 points, and a perfect 15/15 still has a lower bound of about 80 %.
- The rate at which all required fields are correct.
- **Review behaviour** (`reviewBehaviour` in metrics.json): how many wrong values were flagged for review vs accepted silently at high confidence (the safety property that matters), and how often correct values were flagged unnecessarily. On the synthetic smoke set: 0 wrong values; 4 of 40 correct values flagged (10 %).
- Latency: mean, median, p95 and max per image. VLM calls, API failures and estimated cost.

## Failure analysis

Each failed image gets reasons derived from evidence, never guessed. Examples: "OCR confusion on total (expected amount not in OCR text)", "Amount confusion (correct total read by OCR, different line chosen)", "Date-format ambiguity", "Merchant recognition failure", "Incorrect classification (evidence …)", "Category ambiguity", "Arithmetic inconsistency flagged", plus image conditions from the quality analyser (blur, glare, low light, …).

## Leakage prevention

- The HR images are git-ignored, and nothing under `dataset/hr_assignment` can be read by `training/` (`training/common.py` → `assert_not_hr_assignment` raises for any path under `dataset/hr_assignment`; covered by a test).
- `training/scripts/split_dataset.py` splits **by `document_group_id`** (assign one id per physical bill or per merchant series), so near-duplicates never span train and test. `validate_dataset.py` reports exact duplicates (SHA-256) as errors and near-duplicates (dHash) across different groups as warnings.
- Rules and thresholds were developed on synthetic fixtures only.

## Interpreting results

A small set says whether the system works on *these* bills. It does not say how it performs on all bills. Report the confidence intervals, the failure reasons and the conditions of each image, and do not claim more than that.
